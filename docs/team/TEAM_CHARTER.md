# 团队章程 (Team Charter)

## Order App 开发团队

---

## 一、团队愿景

**"让每一笔账、每一件货都在掌控之中"**

打造一款简单易用、数据本地优先的记账与库存管理应用，服务于小微商户和个人用户。

---

## 二、团队目标

| 目标类型 | 描述 | 衡量指标 |
|---------|------|----------|
| **质量** | 代码高质量，零 P0 Bug 上线 | P0 Bug < 3 |
| **进度** | 按 Sprint 交付 | 按时交付率 > 90% |
| **技术** | 架构清晰，可维护 | 技术债务 < 5% |
| **协作** | 高效沟通，信息透明 | Daily 出席率 100% |

---

## 三、角色与职责

### 产品经理 (PM) - 1人
- 制定产品路线图
- 编写 PRD 和需求文档
- 优先级排序 (P0/P1/P2)
- 用户反馈收集与分析
- Sprint 演示主持

### 技术负责人 (Tech Lead) - 1人
- 系统架构设计
- 技术选型决策
- Code Review 审核
- 性能优化把控
- 技术债务管理

### Flutter 开发 - 2人
- 功能开发与单元测试
- 代码质量保证
- 参与架构讨论
- 配合 QA 测试

### UI/UX 设计 - 1人
- 界面设计稿
- 交互体验优化
- 设计系统维护
- 图标与插画资源

### 测试工程师 (QA) - 1人
- 测试用例编写
- 功能测试执行
- Bug 追踪与管理
- 回归测试计划

### 项目经理 (PM) - 1人
- Sprint 计划制定
- 进度跟踪与风险预警
- 团队协调与沟通
- 会议组织与记录

## 四、团队规范

### 代码规范
- 遵循 [Flutter 官方风格指南](https://dart-lang.github.io/styleguide/)
- 使用 `flutter analyze` 确保无警告
- 提交前运行 `flutter test`
- PR 需要至少 1 人 Review 通过

### Git 工作流
```
main (生产环境)
  └── develop (开发分支)
        └── sprint/N-feature (功能分支)
```

### 分支命名规范
```
sprint/1-account-crud
sprint/2-transaction-list
feature/smart-categorization
bugfix/fix-login-crash
hotfix/critical-security
```

### Commit 规范
```
<type>: <subject>

Types:
  - feat: 新功能
  - fix: Bug 修复
  - docs: 文档更新
  - style: 代码格式
  - refactor: 重构
  - test: 测试相关
  - chore: 构建/工具

Examples:
  feat: 添加账户管理列表页
  fix: 修复预算计算精度问题
  docs: 更新 README
```

## 五、会议机制

### Daily Standup (每日站会)
| 项目 | 说明 |
|------|------|
| 时间 | 每天 10:00 |
| 时长 | 15 分钟 |
| 形式 | 站立，轮流发言 |
| 参与 | 全体团队成员 |

**发言模板：**
> 昨天完成了 X
> 今天计划做 Y
> 遇到的问题 Z

### Sprint Planning (Sprint 计划会)
| 项目 | 说明 |
|------|------|
| 时间 | Sprint 第 1 天 |
| 时长 | 2 小时 |
| 参与 | 全体团队成员 |
| 输出 | Sprint Goal、Sprint Backlog |

### Sprint Review (Sprint 评审)
| 项目 | 说明 |
|------|------|
| 时间 | Sprint 最后 1 天 |
| 时长 | 1 小时 |
| 参与 | 全体 + 利益相关者 |
| 输出 | 可演示版本 |

### Sprint Retro (Sprint 回顾)
| 项目 | 说明 |
|------|------|
| 时间 | Sprint Review 之后 |
| 时长 | 1 小时 |
| 参与 | 全体团队成员 |
| 输出 | 改进事项清单 |

### Code Review
| 项目 | 说明 |
|------|------|
| 频率 | 随时 |
| 时长 | 按需 |
| 参与 | Dev1 + Dev2 + Tech Lead |
| 要求 | 所有 PR 必须 Review |

## 七、决策机制

### 决策层级

| 级别 | 决策事项 | 决策人 |
|------|----------|--------|
| **L1** | 日常开发任务 | 开发者 |
| **L2** | 功能细节设计 | Tech Lead |
| **L3** | 架构变更、技术选型 | Tech Lead + PM |
| **L4** | 重大需求变更、延期 | 全体 + 管理层 |

### 决策原则
1. **数据驱动** - 决策基于数据和证据
2. **共识优先** - 争取团队共识
3. **谁负责谁决策** - 避免责任模糊
4. **记录决策** - 重要决策写入文档

## 八、风险管理

### 风险识别

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| 人员离职 | 低 | 高 | 文档充分、知识共享 |
| 技术难题 | 中 | 中 | 预留缓冲、技术调研 |
| 需求变更 | 高 | 中 | 敏捷响应、Sprint 调整 |
| 进度延迟 | 中 | 高 | 优先 P0、砍 P2 |

### 风险跟踪
- 每周 Sprint Review 回顾风险
- 高风险项升级处理
- 保持风险清单更新
